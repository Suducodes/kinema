# KINEMA — architecture (working name)

> A real-time, uncertainty-aware digital twin of human gait that answers
> **"what happens to walking if this body changes?"** in milliseconds,
> where the physics behind each answer took minutes to hours of OpenSim.

Stack: **OpenSim + Moco** (physics) · **Python** (design, learning, stats; MATLAB/Simscape deferred to Phase 7) ·
**Blender** (anatomy, rig, renders) · **Three.js** (live twin) · **Claude** (orchestration, code, Blender MCP, writing).
Imaging personalisation is deliberately deferred to Phase 7.

---

## 1. The research claim (what makes it paper material)

> **Updated after the Phase 0 search (see `paper/novelty_memo.md`):** Bidirectional
> GaitNet (SIGGRAPH 2023) already does forward + inverse gait ↔ weakness. The lead
> claim is now **identifiability-aware amortised Bayesian inference** (simulation-based
> inference over Moco predictive sims), with the identifiability map as the headline
> result. Points 1–4 below still hold, but point 4 becomes a full posterior.

Surrogates of *tracking* simulations (inverse kinematics / dynamics) already
exist, so that alone is **not** novel. KINEMA targets *predictive* simulation:

> **Amortised predictive gait simulation.** Moco predictive simulations invent a
> gait from scratch for a given body (no motion data needed), so they can show
> how people *compensate* for a weak muscle. They are too slow to explore
> interactively. We learn the mapping
> `body + impairment parameters → predicted gait, muscle activity, joint loads`
> with:
> 1. **calibrated uncertainty** (the twin says when it doesn't know),
> 2. **active learning** (the surrogate chooses which expensive simulations to run next),
> 3. **a physics audit** (any surrogate output can be re-checked through OpenSim inverse dynamics, which yields a residual-force "honesty score"),
> 4. **inverse mode** (given an observed gait abnormality, search the differentiable surrogate for the impairment that best explains it).

The contributions to measure are speed-up vs error, the number of simulations
saved by active learning vs random sampling, calibration quality, and inverse-mode
recovery accuracy.

**Integrity rules**, which apply to every phase:
- Novelty gate before building (Phase 0). If prior work already does 1–4, we re-scope rather than overclaim.
- Freeze the held-out test set before any surrogate is trained. Never tune on it.
- Every number in the paper is regenerated by a script from versioned data. No hand-edited figures.
- Clearly separate *synthetic validity* (agrees with Moco) from *physiological validity* (agrees with real gait data or the literature). Claim only what we test.
- Limitations are stated up front: a planar model first, generic (unpersonalised) anatomy, and simulated rather than patient data.
- Release the code, the dataset and the trained models.

```
           ┌──────────── Phase 1 ─────────────┐
 params ──►│ OpenSim/Moco predictive sim      │──► trajectories, activations,
 (θ)       │ (Python, conda env)              │    joint loads, convergence info
           └──────────────▲───────────────────┘
                          │ θ to run next
 ┌──── Phase 2 ──────────┴──────────┐        ┌──── Phase 3 (Python) ─────────┐
 │ Data factory: design (LHS),      │ data   │ Surrogate: GP baseline + NN    │
 │ batch runner, active learning,   │──────► │ ensemble, uncertainty,         │
 │ provenance, HDF5/Parquet store   │◄────── │ physics audit, inverse mode    │
 └──────────────────────────────────┘ "where │ → ONNX export                  │
                                       unsure"└──────────────┬────────────────┘
 ┌──── Phase 4 (Blender, via MCP) ──┐                       │ model.onnx
 │ OpenSim bones (.vtp→mesh), muscle│ rig.glb               ▼
 │ tubes, rig, materials, renders   │──────────► ┌──── Phase 5 (Web twin) ────┐
 └──────────────────────────────────┘            │ Three.js + onnxruntime-web │
                                                 │ sliders, ghosts, audit,    │
                                                 │ inverse mode               │
                                                 └────────────────────────────┘
```

**Data contracts**, the only interfaces between phases:
- `params.schema.json` defines each parameter's name, unit, range and prior. For example: muscle-group strength scale (0.3–1.0), body mass, height, walking speed, tendon stiffness.
- `run/<hash>/` holds `params.json`, `solution.sto`, `summary.parquet` (gait-cycle time-normalised to 101 points), `meta.json` (solver status, iterations, wall time, OpenSim/Moco version, git SHA).
- `dataset.h5` holds the train, val and frozen test splits, plus a manifest.
- `surrogate.onnx` + `surrogate.meta.json` hold the input/output normalisation and the uncertainty head spec.
- `rig.glb` contains named bones and muscles matching OpenSim names one to one.

## 3. Phases

Each phase ends at a **gate**. If a gate fails, fix it or re-scope. Don't push on.

### Phase 0 — Foundations and the novelty gate
- Use LitForge to search: OpenSim/Moco surrogates, amortised or learned predictive simulation, active learning for biomechanics, inverse musculoskeletal identification.
- Set up a conda env (`opensim-org` channel, pinned versions, which also avoids Smart App Control issues), a git repo (Suducodes) and the folder layout below.
- Write `params.schema.json` v0.
- **Gate:** a one-page novelty memo listing the closest 5–10 papers and exactly what we add beyond them.

### Phase 1 — Simulation engine
- Start with Moco's planar `gait10dof18musc` predictive example. It is fast, at minutes per solve.
- Wrap it as `simulate(θ) → run/<hash>/`: apply the parameters, solve, and extract outputs.
- Check robustness: warm starts from the nearest solved neighbour, flag non-converged runs (and keep them, because failure is also data), and run a mesh convergence study.
- Sanity-check the baseline gait against published normal-gait curves (joint angles, GRF shape).
- **Gate:** the baseline matches the literature qualitatively, the convergence rate is above 90% across the parameter ranges, and wall time per solve is measured.

### Phase 2 — Data factory
- Python (scipy.stats.qmc) generates the initial Latin hypercube design (about 300 points).
- A Python batch runner works in parallel across cores, is resumable and idempotent (hash = params + code version), and logs provenance.
- Freeze the test set now: about 15% of points, plus hand-picked "clinical" cases (weak gluteus medius, weak plantarflexors, weak quadriceps).
- An active-learning loop asks the Phase 3 surrogate where it is most uncertain, simulates those points, and retrains.
- **Gate:** at least 1,000 converged runs, and a dataset card describing distributions, failures and compute used.

### Phase 3 — Surrogate (Python: scikit-learn + PyTorch, pinned conda versions)
- Baselines are nearest neighbour and Gaussian process with PCA on the outputs. The main model is a deep ensemble MLP that predicts PCA coefficients of the trajectories, with the ensemble spread giving the uncertainty.
- **Physics audit:** feed predicted kinematics through OpenSim inverse dynamics and compute residual forces and moments. Large residuals mean the output is physically implausible, which serves as an independent honesty check.
- **Inverse mode:** gradient or Bayesian search over θ to match a target gait feature, with credible intervals.
- Metrics are RMSE per output and joint, speed-up, calibration (coverage of the predicted intervals), active vs random learning curves, and inverse recovery error.
- Export to ONNX.
- **Gate:** errors on the frozen test set are below a threshold set in advance (fixed in Phase 0), and calibration coverage is within ±5% of nominal.

### Phase 4 — Blender anatomy and rig (driven by Claude via the Blender MCP)
- Convert the OpenSim bone geometry (`.vtp`) to meshes, placed in the model's frames.
- Build each muscle as a tube swept along its OpenSim path points, named one to one.
- Create the armature from OpenSim joints.
- Materials: a bone shader, plus a muscle shader driven by an `activation` attribute, with an emission glow at high activation.
- Outputs are `rig.glb` for the web, Cycles hero renders, and a turntable plus "compensation" sequences for the paper and video.
- **Gate:** the rig replays a Phase 1 solution in Blender with joint angles matching to 0.1°.

### Phase 5 — The live twin (web)
- Use Three.js with `onnxruntime-web`. The surrogate runs in the browser, so there is no server.
- **Awe features:**
  - **Live compensation:** drag "gluteus medius strength" down and watch the pelvis drop and the trunk lean emerge in real time.
  - **Ghosts of uncertainty:** translucent alternative bodies sampled from the ensemble. Where the model is unsure, you can see it.
  - **Physics audit button:** on demand, shows the residual-force "honesty meter", precomputed or server-side.
  - **Healthy vs impaired** side by side, with joint-load heat on the cartilage surfaces.
  - **Inverse mode:** load an abnormal gait clip and the twin proposes which muscles are likely weak, with confidence.
  - **Cinematic mode:** Blender-rendered intro, then a seamless handoff to the live scene.
- **Gate:** 60 fps on a mid-range laptop, inference under 10 ms, and works offline.

### Phase 6 — Validation and paper
- Experiments: (1) accuracy vs speed, (2) active vs random sample efficiency, (3) calibration, (4) physics-audit residuals, (5) inverse-mode recovery, (6) qualitative comparison of the clinical cases with known compensations from the literature (e.g. Trendelenburg gait).
- Ablations: no active learning, no ensemble, and different PCA dimensions.
- All figures come from `paper/figures/*.py` run on `dataset.h5`.
- Venue ladder: EMBC 2027 (fast, 4 pages) → full paper in IEEE TNSRE / J. Biomechanics / PLOS Comp Bio, with data and code release (Zenodo DOI).
- **Gate:** an internal reproducibility run, a fresh clone that regenerates every figure.

### Phase 7 — Moonshot extensions (each one is a follow-up paper)
- **3D model** (Rajagopal), with the same pipeline at higher compute.
- **Imaging personalisation:** MRI/CT segmentation (SSL4MIS lineage) → subject-specific bones and muscle volumes → θ. Plus the question of how segmentation error propagates to the predicted gait.
- **Video in:** MediaPipe pose → inverse mode → suspected impairment from a phone video.
- **Assistive device design:** add an exoskeleton torque to θ and optimise the assistance profile through the surrogate. This is where MATLAB returns: Simulink/Simscape for the controller and device model, if a license is available.

## 6. Key risks

| Risk | Mitigation |
|---|---|
| Moco fails to converge across wide parameter ranges | Warm starts, narrower priors, log failures as data |
| Novelty already taken | Phase 0 gate; differentiators are uncertainty + active learning + audit + inverse mode |
| Planar model judged too simple | Framed as method paper; 3D is Phase 7 |
| Compute | Planar model is minutes per solve; active learning cuts runs; overnight batches |
| Blender-to-web fidelity | Names matched one to one with OpenSim; Phase 4 gate replays exact solutions |
